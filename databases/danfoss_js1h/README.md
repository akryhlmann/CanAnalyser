# Danfoss JS1-H heavy duty joystick: CAN databases

Built from the Danfoss technical information *JS1 Heavy Duty Joysticks*,
BC171886484518en-001601 (rev. 1601, April 2026). The appendices used are
"CAN J1939 protocol" and "CAN+ and CANopen protocol".

> These files are **reconstructions from the manual, not official Danfoss
> files**. Danfoss publishes an official CANopen EDS for the JS1-H (see the
> manual, page 84). Use that one when you can get it, and check these files
> against a real joystick.

| File | Use for model code (base "C" field) |
|---|---|
| `js1h_j1939.dbc` | CJP/CJH (CAN J1939), CSP/CSH (CANalog J1939), CLP/CLH (CAN+ J1939) |
| `js1h_can.eds` | CPP/CPH (CANopen), CTP/CTH (CANalog CANopen) |
| `js1h_canplus.eds` | CMP/CMH (CAN+ CANopen) |

The files are generated by `tools/make_js1h_databases.py`. Edit the script,
not the files, and re-run it. `tests/test_js1h_databases.py` checks that the
files match the script and decode frames laid out as the manual describes.

## Using them in CanAnalyser

```
cananalyser --dbc databases/danfoss_js1h/js1h_j1939.dbc
cananalyser --eds databases/danfoss_js1h/js1h_can.eds:16      # node ID 16 (0x10)
```

Or use **Load DBC… / Load EDS…** in the toolbar. For an EDS, enter the
joystick's node ID when asked.

## J1939 contents

All four messages use priority 3, are 8 bytes long and are sent every 20 ms
at 250 kbit/s.

| Message | PGN | Contents |
|---|---|---|
| BJM1 | 64982 (0xFDD6) | Base X/Y: neutral, negative and positive status; position; detents; buttons 1–12 |
| EJM1 | 64983 (0xFDD7) | Grip X/Y proportional inputs: status, position and detents |
| BJM3 | 64986 (0xFDDA) | Same layout as BJM1 |
| EJM3 | 64987 (0xFDDB) | Same layout as EJM1 |

- **Position:** 10 bits, 0–1000 counts = 0–100 % of travel. The DBC scales
  it as 0.1 %/count. The value is a magnitude; the direction comes from the
  negative/positive status bits. 1022 means a sensor error and 1023 means the
  axis is not available; CanAnalyser shows these as `error` and `n/a`.
- **2-bit status values** have value tables: 0 = off/not pressed, 1 = on/pressed,
  2 = error, 3 = not available.
- **DM1 faults:** SPN 2660 (X), 2661 (Y), 2662 (grip X), 2663 (grip Y) and
  2664 (grip theta), each with FMI 3 (voltage high), 4 (voltage low),
  13 (not calibrated) or 14 (redundant input failure). SPNs 2660–2663 are
  attached to the BJM1/EJM1 position signals so faults show a name. SPN 2664
  has no signal in these messages, so it shows as a number.
- **Source address:** the joystick's SA depends on the model code (the "E—CAN"
  field). The DBC uses 0xFE as a placeholder. CanAnalyser and other
  J1939-aware tools match on PGN, so any SA decodes.

## CANopen contents

- **Heartbeat:** 20 ms by default (object 1017h).
- **EMCY:** COB-ID 80h + node ID.
- **SDO:** expedited transfers, plus segmented upload for strings.
- **LSS:** used to set node ID and bitrate.
- **TPDOs:** all event-driven, every 20 ms by default (event timer), with COB-IDs per the predefined connection set.

| PDO | COB-ID | CAN / CANalog | CAN+ |
|---|---|---|---|
| TPDO1 | 180h + node | Freeze byte, buttons 1–24 pressed, reserved byte, buttons 1–24 enabled (8 bytes) | Freeze byte, buttons 1–12, 4 bits reserved, buttons 13–24, 4 bits reserved, buttons 1–12 enabled (7 bytes) |
| TPDO2 | 280h + node | X and Y axes (S16, 0.1 %), reserved 16 bits, X/Y neutral states (2 bits each), reserved 2 bits | same |
| TPDO3 | 380h + node | Grip 1–3 (S16, 0.1 %), grip 1–3 neutral states | same |
| TPDO4 | 480h + node | – | Analog inputs X100 pins 11, 12, 30, 15 (S16, 0.1 %) |

**Neutral state values** (6404h): 0 = neutral, 1 = out of neutral, 2 = error,
3 = not available.

**EMCY codes:**

| Input | Voltage high | Voltage low | Not calibrated | Redundancy |
|---|---|---|---|---|
| X | 0x3110 | 0x3120 | 0xFF10 | 0xFF20 |
| Y, grip X, grip Y, grip theta | same codes | | | |

EMCY byte 3 is an occurrence counter (0–127). Byte 4 identifies the sensor:
0x80 = X, 0x81 = Y, 0x82 = grip X, 0x83 = grip Y, 0x84 = grip theta. The
error register sets bit 2 for voltage errors and bit 7 for grip
communication or calibration errors.

## Discrepancies in the manual and how they were resolved

1. **COB-IDs written as "180h + Node Id + 230".** "230" is 2³⁰ with the
   superscript lost, i.e. bit 30 (no RTR). Default = 0x40000180 + node ID.
2. **TPDO1 mapping count, CAN/CANalog** (1A00h sub 0 = 49, but 50 entries
   are listed). The EDS uses all 50, which fills exactly 8 bytes.
3. **Duplicated mapping entries.** 1A00h sub 6 (button 5) repeats 60200401h,
   and on CAN+ so does sub 7 (button 6). These were corrected to 60200501h and
   60200601h.
4. **6020h sub-index layout.** The object table puts "Freeze bit 1–8" at
   sub 1–8 and buttons at sub 9–56, but every PDO mapping entry points at
   pressed status in sub 1–24 and enabled status in sub 25–48. The EDS
   follows the mappings, since that is what is on the bus. SDO reads of 6020h
   may therefore show the wrong button names.
5. **CAN+ TPDO4 COB-ID** (1803h) is listed as 380h + node ID, the same as TPDO3.
   The EDS uses 480h + node ID, the predefined default for TPDO4.
6. **1017h** is U16 but its maximum is given as 2³²−1. The EDS keeps U16.
7. **6000h sub 0** gives a maximum of 1, but two sub-indices are documented.
   **6405h sub 0** is typed U16. The EDS uses 2 and U8.
8. **CAN+ 6404h value list** reads "12 – Error, 13 – Not available". These are
   typos for binary 10 and 11, i.e. 2 and 3.
9. **Mapping lengths.** U8 objects are mapped with 1, 2 or 4 bits, exactly as
   the manual specifies. CanAnalyser handles this, but strict CANopen
   configuration tools may warn about it.
10. **Data type 40h NEUTRAL_STATE** (custom 2-bit type) is not defined in the
    EDS. The neutral states are U8 objects with a description.
11. **J1939 data field example 3** labels byte 2 bits 5–6 as "X-axis lever
    forward". The parameter table says Y-axis; the DBC follows the table.
12. **The J1939 appendix says 250 kbit/s**, but the model code also lists
    125 and 500 kbit/s options (B…/D… codes). Set the bitrate to match your
    part.
13. **Node IDs in the model code** ("Node ID 10, 13, 16, 1C, 33–36, 90, 93, 96,
    9C") are probably hexadecimal, since "9C" is not a decimal number. Values
    above 7Fh cannot be CANopen node IDs, so those codes are presumably J1939
    source addresses. Check against your part before relying on this.
